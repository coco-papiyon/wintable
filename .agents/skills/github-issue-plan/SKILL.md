# github-issue-plan

## 入力と開始条件

GitHub CLI（gh）がインストール・認証済みであることを前提とする。GitHub操作は通常のghコマンドを使い、不足する操作はgh apiで行う。MCPとチャットのGitHubアプリ連携は使用しない。開始時の認証・対象確認とアクセス拒否時の承認付き実行は共通ルールに従う。

入力はIssue番号。対象リポジトリと組み合わせて解釈する。必要な入力がない、または対象が一意でない場合は確認する。

実行前に[共通ルール](references/workflow-rules.md)を必ず読み、Agent・機能・権限の確認、排他的ラベル更新、回数管理と再実行、要件判定を適用する。報告時は同ファイルの投稿テンプレートを使う。

実行依頼は以下に明記したIssue本文更新・ラベル変更等の許可として扱う。ユーザーが範囲を限定した場合は従い、環境の権限・承認要件は維持する。

## 作業前の必須手順

[共通ルールの「作業前の最新ソース取得」](references/workflow-rules.md#作業前の最新ソース取得全スキル必須)を実施する。対象remoteをfetchし、最新の対象ブランチと比較先のSHAを確認する。変更作業では作業ツリーも同期し、読み取り専用なら取得したSHAのソースを使う。未コミット変更や未pushコミットは保護する。取得・同期を完了してから以下の手順へ進み、最新取得に失敗したまま古いソースで続行しない。

コメント・ラベルの更新先は対象Issueのみ。計画はIssue本文を更新し、検証OK時のPR作成・本文設定は行う。PRへの報告コメントやラベル設定はしない。

## 手順

試験の計画・実行・結果評価では[試験選択スキル](../wintable-test/SKILL.md)と[試験方針](../../../docs/testing.md)を適用する。通常は変更に応じた試験に絞り、関連コード・契約を変更した場合は対応する最大値・障害・実SSH試験を追加する。計画時は実施区分と選択理由を計画へ記載する。必須要件と配布前ゲートを省略せず、未実施範囲と理由を報告する。

1. Issue本文と全コメント、関連コード・開発手順を読む。
2. 要件、現状、変更対象、実装手順、検証方法、依存事項・未確定事項を整理して実装計画を作る。
3. 元の要件・背景・受け入れ条件を保持し、Issue本文に実装計画を反映して書き替える。計画は `<!-- github-workflow:plan:start -->` と `<!-- github-workflow:plan:end -->` で囲む。初回は本文末尾へ追加し、再実行では計画ブロックだけを更新する。計画は作業内容が分かるレベル1見出しから始める。計画コメントの投稿、コード変更、PR作成は行わない。更新直前に本文を再取得して他者の変更を保持し、可能なら更新時刻の一致条件を利用する。マーカーの重複・欠落で範囲を確定できない場合は上書きせず確認する。
4. 更新後の本文を再取得して計画の反映と元の記載の保持を確認した後、Issueのステータスを `status:planned` に置換する。本文更新失敗時はラベルを変更しない。

完了報告にはIssue URL、本文へ反映した計画の要点、付与したラベルを含める。計画コメントURLは作成しない。本文更新とラベル更新の成否を区別し、再実行時は計画を重複追加せず未完了操作だけを行う。

## 完了と途中失敗

最終報告は作業内容が分かるレベル1見出しで始め、対象Issue URL、本文の更新結果、該当するブランチ・SHA・ラベル、検証結果、実行Agentと実行方法を記載する。

外部操作の成功は再取得して確認する。途中失敗は完了と未完了を区別し、同じ操作を無制限に再試行しない。対象不一致、権限不足、未解決の競合などで続行できない場合は原因と必要な対応を報告する。再実行は既存記録とリモート状態から未完了部分だけ再開する。
