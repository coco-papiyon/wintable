# wintableの試験選択

リポジトリルートの[試験一覧と実行方針](../../../docs/testing.md)を読み、変更差分と要件から実施範囲を決める。既存テスト名・スクリプトが変わっていればコードを正とし、文書の選別例をそのまま使わない。

- 通常は変更したパッケージと利用側のGo試験、小入力の正常・異常系、安価なGo境界、必要なvet / buildを選ぶ。最大値の実プロセス転送、Docker実SSH、配布作成は毎回起動しない。
- 上限・引用・直列化・receiver・transport・出力取得・ファイル確定等を変更した場合、文書の対応表から関連する最大値・障害・実SSH試験を追加する。共通コード変更は両OSへの影響を確認する。新機能で境界契約を導入する場合も同じ。
- Issueの必須要件、明示された全件試験、配布・公開ゲートを優先する。通常試験の選別を理由に必須ケースを省略したり、既存ゲートの期待値を緩めたりしない。
- 文書・スキルだけなら差分・参照先・スキル形式を検証する。製品試験は不要。

実行前に試験区分、対象、選択理由を短く伝える。現行のgo test ./...はWindows実プロセスと最大値を含み、-shortは効かない。-run / -skipで選び、単一関数に混在して選べない場合は関連変更時に全体を実行する。無関係な最大値を外す目的で試験を削除しない。

fixture環境変数があると試験範囲が変わるため確認する。秘密値は出力しない。成功済み試験はSHAと範囲を確認して再利用し、失敗・追加変更・未解決懸念がないのに反復しない。

報告には対象SHA、区分、実行コマンドと結果、省略範囲と理由を記載する。必要なのに実行不能な試験は未確認とし、通常試験合格を両OS全受入合格と扱わない。このスキル自身はcommit / push / GitHub投稿を許可しない。
