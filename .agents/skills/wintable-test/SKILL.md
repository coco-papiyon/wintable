# wintableの試験選択

リポジトリルートの[試験一覧と実行方針](../../../docs/testing.md)を読み、変更差分と要件から実施範囲を決める。既存テスト名・スクリプトが変わっていればコードを正とし、文書の選別例をそのまま使わない。

- 通常の実装・修正・検証・レビューは `go test ./... -count=1` の全Go試験とLinux実SSH（transportと対象製品モジュール）合格まで確認して終了する。全Go試験内の境界試験は省略しない。
- Windows実SSH、複数CLIによる並列取得、監査、license・ZIP検査・導入・両OS証跡集約は配布物作成時に実施する。共通コード変更やIssueの配布受入条件を理由に、通常実装で配布一式を自動実行しない。今回の作業で全受入が明示依頼された場合はその指定に従う。
- Linux試験用exeは通常buildし、監査・ZIPを伴うdistribution.ps1 / package.ps1 / complete-local.ps1を通常確認のために呼ばない。Linux runnerは製品試験も指定する。新モジュールの対象漏れと文書例の配布manifest依存を確認し、必要なら未梱包exe用のLinux製品試験経路を用意する。
- 配布時は両OS実SSH・並列CLI取得・監査・ZIP検査と既存公開ゲートを省略しない。配布時の項目は通常実装の不合格理由にせず、配布時確認として報告する。
- 文書・スキルだけなら差分・参照先・スキル形式を検証する。製品試験は不要。

実行前に通常実装か配布物作成かを短く伝える。通常実装の全Go試験を-run / -skipで削らない。全Go試験にはWindowsローカル実プロセスと最大値が含まれる。追加の最大値・障害試験は該当コード修正時に必要なものを選ぶ。-shortだけでは軽量化しない。

fixture環境変数があると試験範囲が変わるため確認する。秘密値は出力しない。成功済み試験はSHAと範囲を確認して再利用し、失敗・追加変更・未解決懸念がないのに反復しない。

報告には対象SHA、区分、実行コマンドと結果、省略範囲と理由を記載する。必要なのに実行不能な試験は未確認とし、通常試験合格を両OS全受入合格と扱わない。このスキル自身はcommit / push / GitHub投稿を許可しない。
