# github-pr-approbe

## 入力と開始条件

入力はPR番号。対象リポジトリと組み合わせて解釈する。必要な入力がない、または対象が一意でない場合は確認する。

実行前に[共通ルール](references/workflow-rules.md)を必ず読み、Agent・機能・権限の確認、排他的ラベル更新、回数管理と再実行、要件判定を適用する。報告時は同ファイルの投稿テンプレートを使う。

実行依頼は以下に明記した投稿・ラベル変更・push等の許可として扱う。ユーザーが範囲を限定した場合は従い、環境の権限・承認要件は維持する。

## 手順

1. PR本文・全コメント・レビュー・head/baseを取得し、関連Issueを特定して本文と全コメントを読む。
2. Issueの要件一覧を作り、PR差分・関連コード・テストをレビューする。要件充足に加えて、変更に起因する不具合や回帰も確認する。
3. 要件別判定、根拠、レビュー指摘、全体OK/NG、検証したSHAをPRコメントへ投稿する。
4. NGならPRレビューを `REQUEST_CHANGES` として提出し、PRを `status:changes-requested-n`、Issueを `status:changes-requested-n` にする。PRとIssueの回数は独立に算出し、同じ値とは限らない。PRコメントにPRのNG回数記録を残し、IssueにもNG結果へのリンクとIssueの要修正回数記録を残す。レビュー提出に失敗しても確定したNG結果の投稿と要修正ラベル更新は行い、提出失敗を別途報告する。
5. OKならPRレビューを `APPROVE` として提出し、PRを `status:approved` にする。PR本文に対象Issueの正しい `Closes` 指定があることを確認し、不足していれば追記する。最新head、必須チェック、必須承認、マージ可能性を確認し、リポジトリで許可された方法でマージする。
6. マージ成功を再取得して確認した後、Issue・PRをそれぞれ `status:merged` にする。以下の自動クローズ手順で対象Issueが `CLOSED` になったことを確認し、Issue URLとクローズ結果を報告する。

### マージ時のIssue自動クローズ

- 既定ブランチへのマージでは、PR本文の `Closes` 指定によるGitHubの自動クローズを利用する。PRコメントへの記載だけで代用しない。
- 既定ブランチ以外へのマージではGitHubのキーワードによる自動クローズが働かないため、マージ成功確認後にスキルが対象Issueを完了理由でクローズする。自動クローズのためだけにPRのbaseを変更しない。
- 既定ブランチへのマージ後もIssueがopenの場合は、状態を再取得し、マージ成功と対象Issueの対応を確認したうえでスキルがクローズする。既にclosedの場合は重ねて操作しない。
- マージ前、マージ失敗時、自動マージの予約段階ではIssueをクローズしない。クローズ権限不足やAPIエラーの場合は、PRマージ成功とIssueクローズ未完了を分けて報告し、完了扱いにしない。
- GitHubの挙動の根拠：[PRとIssueのリンク（GitHub Docs）](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)。

自己承認不可、権限不足、未完了の必須チェック、競合などで承認・マージできない場合は、レビューOKと操作未完了を区別して報告する。保護ルールを迂回せず、承認を偽装しない。自動マージ予約をマージ完了として扱わない。

## 完了と途中失敗

最終報告は作業内容が分かるレベル1見出しで始め、対象URL、操作結果、コメントURL、該当するブランチ・SHA・ラベル、検証結果、実行Agentと実行方法を記載する。

外部操作の成功は再取得して確認する。途中失敗は完了と未完了を区別し、同じ操作を無制限に再試行しない。対象不一致、権限不足、未解決の競合などで続行できない場合は原因と必要な対応を報告する。再実行は既存記録とリモート状態から未完了部分だけ再開する。
