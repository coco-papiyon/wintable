# github-pr-fix

## 入力と開始条件

入力はPR番号。対象リポジトリと組み合わせて解釈する。必要な入力がない、または対象が一意でない場合は確認する。

実行前に[共通ルール](references/workflow-rules.md)を必ず読み、Agent・機能・権限の確認、排他的ラベル更新、回数管理と再実行、要件判定を適用する。報告時は同ファイルの投稿テンプレートを使う。

実行依頼は以下に明記した投稿・ラベル変更・push等の許可として扱う。ユーザーが範囲を限定した場合は従い、環境の権限・承認要件は維持する。

## 手順

1. PR本文・全コメント・レビューから修正要求を読み、head名と関連Issueを特定し、Issue本文と全コメントを読む。
2. 指摘と要件の対応を整理し、PRのheadブランチで修正する。要件との矛盾や未対応事項を明示する。
3. 対応するテストと必要な回帰確認を実行し、commit・pushする。
4. PRコメントへ、指摘ごとの対応、変更箇所、検証結果、commit SHA、未解決事項を投稿する。Issueにも修正報告へのリンクと実装回数記録を投稿する。
5. Issueのステータスを `status:implementation-n` に置換する。PRを `status:fix-n` に置換し、他のステータスラベルを削除する。PRコメントに修正回数と機械可読記録を残し、レベル1見出しにも「修正n回目」を含める。未解決事項を明記し、修正回数の更新をレビュー合格として扱わない。

このスキル内でレビュー合格・承認・マージを確定しない。未修正の指摘を解決済みにしない。

## 完了と途中失敗

最終報告は作業内容が分かるレベル1見出しで始め、対象URL、操作結果、コメントURL、該当するブランチ・SHA・ラベル、検証結果、実行Agentと実行方法を記載する。

外部操作の成功は再取得して確認する。途中失敗は完了と未完了を区別し、同じ操作を無制限に再試行しない。対象不一致、権限不足、未解決の競合などで続行できない場合は原因と必要な対応を報告する。再実行は既存記録とリモート状態から未完了部分だけ再開する。
