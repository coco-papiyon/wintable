# github-pr-resolve-conflicts

## 入力と開始条件

GitHub CLI（gh）がインストール・認証済みであることを前提とする。GitHub操作は通常のghコマンドを使い、不足する操作はgh apiで行う。MCPとチャットのGitHubアプリ連携は使用しない。開始時の認証・対象確認とアクセス拒否時の承認付き実行は共通ルールに従う。

入力はPR番号。省略時は現在ブランチのopen PR。対象リポジトリと組み合わせて解釈する。必要な入力がない、または対象が一意でない場合は確認する。

実行前に[共通ルール](references/workflow-rules.md)を必ず読み、Agent・機能・権限の確認、排他的ラベル更新、回数管理と再実行、要件判定を適用する。報告時は同ファイルの投稿テンプレートを使う。

実行依頼は以下に明記した投稿・ラベル変更・push等の許可として扱う。ユーザーが範囲を限定した場合は従い、環境の権限・承認要件は維持する。

## 作業前の必須手順

[共通ルールの「作業前の最新ソース取得」](references/workflow-rules.md#作業前の最新ソース取得全スキル必須)を実施する。対象remoteをfetchし、最新の対象ブランチと比較先のSHAを確認する。変更作業では作業ツリーも同期し、読み取り専用なら取得したSHAのソースを使う。未コミット変更や未pushコミットは保護する。取得・同期を完了してから以下の手順へ進み、最新取得に失敗したまま古いソースで続行しない。

コメント・レビュー・ラベルの更新先は対象PRのみ。関連Issueは要件の読み取りだけに使い、コメント・本文・ラベル・回数は更新しない。マージ成功後のIssueクローズだけは行う。競合解消後のPRステータスは `status:fix-1` に設定する。

## 手順

試験の計画・実行・結果評価では[試験選択スキル](../wintable-test/SKILL.md)と[試験方針](../../../docs/testing.md)を適用する。通常は変更に応じた試験に絞り、関連コード・契約を変更した場合は対応する最大値・障害・実SSH試験を追加する。計画時は実施区分と選択理由を計画へ記載する。必須要件と配布前ゲートを省略せず、未実施範囲と理由を報告する。

1. PRを特定し、本文・全コメント・レビュー、head/base、関連Issue本文と全コメントを読む。
2. headとbaseの最新状態を取得し、PRのheadブランチへbaseをmergeして競合を解消する。両ブランチの変更意図とIssue要件を保ち、一括で片側を採用しない。
3. 競合マーカー・未解決ファイルの残存を確認し、影響するテスト・ビルドを実行する。意味を確定できない競合は無理に解消せず、該当箇所と判断事項を報告する。
4. 解消内容をcommit・pushし、PRの最新headとマージ可能状態を再取得する。競合がない場合は変更せず、その旨を報告する。
5. 競合解消のpush成功を確認したら、共通ルールの排他更新に従い、対象PRの他のステータスラベルを削除して `status:fix-1` を設定する。更新後にラベルを再取得して確認する。競合がなかった場合や解消・pushが未完了の場合は変更しない。
6. PRコメントへ、取り込んだbase SHA、競合箇所、解消方針、検証結果、commit SHA、設定したラベル、残る問題を投稿する。

コンフリクト解消後のラベルは既存の番号にかかわらず固定で `status:fix-1` とし、この操作でPR修正回数の記録は追加・更新しない。コンフリクト解消だけでは要件検証やレビュー合格を意味しないため、再検証が必要であることを報告する。マージはNo. 4で行う。

## 完了と途中失敗

最終報告は作業内容が分かるレベル1見出しで始め、対象URL、操作結果、コメントURL、該当するブランチ・SHA・ラベル、検証結果、実行Agentと実行方法を記載する。

外部操作の成功は再取得して確認する。途中失敗は完了と未完了を区別し、同じ操作を無制限に再試行しない。対象不一致、権限不足、未解決の競合などで続行できない場合は原因と必要な対応を報告する。再実行は既存記録とリモート状態から未完了部分だけ再開する。
